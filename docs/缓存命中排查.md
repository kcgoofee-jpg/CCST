# 缓存命中排查手册

面向维护者。记录 2026-10「缓存命中持续 0%」两次事故的完整结论、机制真相、修复手段与排查工具。用户侧的自救步骤见 README 常见问题与下文。


## 结论（6.0.0，2026-10-07）

1. **根因**：Claude Code 2.1.267（2026-09-09）起，用自定义系统提示词启动的会话只记录一次系统提示词，续接时沿用（官方 CHANGELOG「record the system prompt and tool definitions once」，同版新增 `--system-prompt-snapshot off`；SDK 文档写明逐账号开启）。CCST 回放旧轮次时连这份记录一起带上，CLI 发出旧的、甚至别的聊天的系统提示词。修法：`systemPrompt` 用 `{ type: 'custom', snapshot: false }`，并过滤 `prompt_snapshot` 附件。`scripts/prompt-recording-probe.mjs` 能测账号是否已开启。
2. **上一轮发言找不回来**：预设后置条目并进发言后按合并文本记录，下一轮按原文找不到 → 历史每轮重写。改为按原文记录。
3. **聊天边界**：以「第一条 user」划系统提示词，Kemini / Izumi（聊天前放 user 条目）整卡每轮重写。改为面板发来聊天首尾消息开头，代理按它划分。
4. **只给最新发言套标签的正则**（Kemini `<interactive_input>`，maxDepth 1）：找回时容忍只差标签和空白。
5. **系统区关键词世界书**：面板发来触发条目原文，代理按原文移到本轮。
6. 实测（Opus 4.6，订阅）：衡 × 军训14天 第 3 轮起 82–88%；木屋求生 × Kemini 从 0% 到第 2 轮 89%；辣妈庄园 × Izumi 仍是 0%，原因是 Izumi 自带脚本每轮改提示词（见 CHANGELOG「已知」）。
7. 用户反馈用面板「复制诊断报告」：报告里有每轮读写、前缀从哪变、酒馆这边改了什么，以及 CLI 实际发出的请求结构。

## 一、缓存的运作原理（为什么能省 90%+）

Anthropic 的提示词缓存按**前缀逐字节比对**：这次请求与上次写入的缓存从第 0 字节起一致的部分按「缓存读」（约 0.1 倍价）计，**第一处不一致之后的全部内容**按「缓存写」（约 1.25 倍价）重算。所以决定成本的不是"改了多少字节"，而是"第一处差异出现在哪个位置"。

长聊每轮只新增最后一句话，理想情况下 90%+ 的 token 走缓存读——前提是**没变的部分一个字节都不能动**。代理的「逐轮还原」（`turn-capture.js`）、系统提示词分段（`system-prompt.js` 的 boundary）、每轮变化块前移（`lore-tail.js`）三件事共同维护这个前提。

## 二、CLI 的真实行为（tap 实测，2026-10-07 修正）

用线级 tap（见第四节）抓 CLI 2.1.285 的真实请求并读回复里的 usage，确认：

1. **缓存有效期**（官方文档 prompt-caching →「Which TTL each request gets」，与 2.1.285 源码 `X0t`/`fLt` 一致）：订阅在**套餐额度以内**时主对话（含 SDK 轮）1 小时；**用超、开始扣额外用量**时降到 5 分钟。Pro / Max 没有区别。优先级：`FORCE_PROMPT_CACHING_5M` > `CLAUDE_CODE_PROMPT_CACHE_TTL` > settings > `ENABLE_PROMPT_CACHING_1H` > 默认。实测（10-07）：CCST 下 CLI 不联网拉服务端开关（`DISABLE_NONESSENTIAL_TRAFFIC`），把缓存的开关白名单改成不含 `sdk` 也仍是 1h；用 tap 在回复头里伪造超额状态也仍是 1h（每轮是新进程，单次请求在拿到回复头前就定了 TTL）——真实环境里 CLI 如何得知超额状态未查实。
2. **计费头不参与缓存**：`system[0]` 是 `x-anthropic-billing-header: cc_version=<版本>.<三位后缀>; cc_entrypoint=…;`。后缀 = `sha256(盐 59cf53e54c78 + 首条用户消息第 4/7/20 个字符 + 版本号)` 前 3 位，所以首轮（fold 路径，首条用户消息是折叠后的整段）和之后的 resume 轮后缀不同。实测后缀变化（8c4→a5e）的那一轮照样读到 27.7k 缓存——服务端不把它算进前缀。
3. **环境加料只在当前轮**：CLI 把 `<system-reminder>` 环境块拼在当前轮用户消息前面，历史轮不带。相邻两轮断在"上一轮最后一条消息"处，只损失最后一小段，属设计行为。
4. **断点**：CLI 打 `cache_control`（带 ttl）在 system 末项与当前轮末尾。历史消息靠尾部断点覆盖的前缀被缓存。

> 旧版本手册曾写「计费头后缀按安装指纹生成、字节 0 一变缓存全废、双安装轮流应答导致持续 0%」。这些结论来自一个有 bug 的 tap：它按字符串拼接 TCP 分片，把跨分片的汉字切成 U+FFFD 再转发，抓到的"差异"是 tap 自己造成的。已作废。

## 三、事故结论

### 第一次（10-05，5.2.0 处理）

SDK 版本没锁（`^0.3.285`），重装会拉到当天发布的新版 CLI；逐轮还原的 pin 不感知版本。5.2.0 锁死 SDK、pin 带版本号、连续异常自动重置。这些修复保留，但**不是**下面这次的原因。

### 第二次（10-07，用户升级到 5.2.0 后仍持续 0%）——未结案

症状：Pro 订阅，Opus 4.6。每轮新发言读缓存≈0（按截图数字倒推：提示词约 63k，读≈0、写≈62.8k，**连系统提示词都没读到**），**重 roll 有命中**；回退、升级、自动重置都无效。单轮回复约 3 分 40 秒、输出 8k。此前（Opus 5.5 发布前）约 20%。

**5.2.0 的修复为什么无效**：它改的是 SDK 版本漂移和 pin 文件，都不是这次出问题的环节。

**已排除**：
- 服务端开关把 SDK 移出 1h 白名单——CCST 下 CLI 不拉开关，实测改白名单无效（见第二节第 1 条）。
- 请求没带面板参数被当成后台请求（后台请求不做逐轮还原）——用户状态页能显示该轮，说明是正式聊天请求。
- 计费头变化、双安装——计费头不参与缓存。

**已知的结构性损耗（解释「之前 20%」，不解释 0%）**：CLI 只给当前轮挂 `<system-reminder>`，逐轮还原（`turn-capture.js`）负责下一轮把它补回；实测带面板参数时稳态逐字一致。9 月 A/B（`cctest1/tavern/ab-tests/结果-M1缓存.md`）：常见预设 45%～57%，世界书全常驻 + 注入进系统 + 逐轮还原才到 95%。

**头号嫌疑**：Pro 额度用超、扣额外用量 → CLI 降到 5 分钟；长回复 + 阅读时间 > 5 分钟 → 整段过期，重 roll 命中。与「连系统提示词都没读到」吻合，有官方文档依据。其他候选：1M 上下文与普通版每轮来回切换（缓存按模型/上下文分开）；代理的系统提示词切分点（`splitAt`）每轮移动。

**需要的数据**：用户的 `data/usage.jsonl` 最后 20 行（只有 token 数、时间和哈希）——看相邻两轮开始时间间隔、`notices` 是否有 `no-1m`、`path`、`cacheDiag.splitAt`；以及是否开了额外用量、最近是否用超。

**5.2.1 已做**：订阅模式也设 `CLAUDE_CODE_PROMPT_CACHE_TTL=1h`（覆盖头号嫌疑）；用量记录 `cacheTtl` + 两轮间隔，面板直接说「过期」；异常文案不再叫人回退 SDK；`wire-diagnosis.mjs` 修 tap 分片 bug 并输出有效期。诊断脚本的请求现在带面板参数（不带会被当成后台请求、不做逐轮还原），跑 4 轮：第 1→2、2→3 轮各有一次预期内的断点（首轮换路径、上下文钉住），第 3→4 轮应逐字一致。

## 五、给用户的修复路径（按顺序）

1. 升级到 5.2.1+（重跑一键安装，或 `git pull && npm install`），重启代理/酒馆。
2. 面板「状态」→ 详情：写着「已过 N 分钟…过期」就是间隔问题（1h 也会过期，属正常）；写着「系统提示词 / 聊天记录从第 N 条起不同」就是预设、世界书或正则在改内容。
3. 还解释不了：跑 `node scripts/wire-diagnosis.mjs`，把输出发给维护者。

## 六、附录：CLI 升级节奏与 clewdr 缓存机制（2026-10-07 取证）

### CLI/SDK 升级频率（官方数据）

- npm `@anthropic-ai/claude-agent-sdk`：9-15 → 10-06 的 22 天发了 **19 个版本**，基本每天一个；10-05 发 0.3.290（CLI 2.1.290）——正是"10-05 缓存 0%"反馈的当天。旧版浮动 `^0.3.285` 时，当天任何一次重装都会拉到新版，时间线完全吻合。
- CHANGELOG 2.1.290 里与请求字节直接相关的条目："修复代理/网关拒绝其中一个 beta 头（非 400 状态，或同时带第二个 beta）时请求失败"（beta 头发送方式变更，影响所有模型）与"修复续接的 subagent 丢失之前的 thinking 与 prompt cache"。
- 2.1.285（我们锁定的版本）则改了"自定义 ANTHROPIC_BASE_URL 会话使用 1M 上下文"。

### 旧线（CLI/SDK）维护协议

锁定版本后不会自动漂移；"调参"只发生在**主动升级**时。升级流程必须是：改 lockfile → 跑 `wire-diagnosis` 对比请求结构 → 跑命中率回归 → 发版。用户报"命中异常"时先问：最近是否重装过（拉到了新 CLI）。

### clewdr 的缓存机制（修正此前结论）

- `anthropic-wire` crate 有**全量 cache_control schema**（含 request 级"缓存整个请求前缀"的标记），但**放置逻辑为零**：订阅（code）通道是透传，断点由下游客户端负责；clewdr 只做检测、哈希，以及把下游断点里的 `scope` 字段剥掉。
- 官方文档（PR #88 `docs/cache_control_usage.md`）写明的机制：检测 system 里带 cache_control 的块 → 哈希 → **粘性 cookie 路由**（同 system prompt 固定同账号，Moka 缓存 1000 条 / 60 分钟 TTL）——这是 **cookie（网页版）通道**的账号级缓存保暖；订阅单账号通道用不上粘性路由。
- 计费头：clewdr 生成的 `claude_code_billing_header` 与 CLI 同一公式（盐 `59cf53e54c78` + 首条用户消息第 4/7/20 字符 + 版本号，sha256 取前 3 位）。它不影响缓存，但新后端照抄以保持请求形态一致。
- **对重写的意义**：clewdr 的实践佐证了"下游不打断点就没有缓存管理"——直连路线上断点必须由代理自己打（即 P2 cache 模块）。可借鉴：request 级 cache_control 标记（比逐块简单）、计费头公式；**断点一律显式写 `ttl: "1h"`**，不留给任何默认值。
