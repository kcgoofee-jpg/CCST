# 缓存命中排查手册

面向维护者。记录 2026-10「缓存命中持续 0%」事故的完整结论、机制真相、修复手段与排查工具。用户侧的自救步骤见 README 常见问题与下文。

## 一、缓存的运作原理（为什么能省 90%+）

Anthropic 的提示词缓存按**前缀逐字节比对**：这次请求与上次写入的缓存从第 0 字节起一致的部分按「缓存读」（约 0.1 倍价）计，**第一处不一致之后的全部内容**按「缓存写」（约 1.25 倍价）重算。所以决定成本的不是"改了多少字节"，而是"第一处差异出现在哪个位置"。

长聊每轮只新增最后一句话，理想情况下 90%+ 的 token 走缓存读——前提是**没变的部分一个字节都不能动**。代理的「逐轮还原」（`turn-capture.js`）、系统提示词分段（`system-prompt.js` 的 boundary）、每轮变化块前移（`lore-tail.js`）三件事共同维护这个前提。

## 二、CLI 的真实行为（tap 实测，修正旧认知）

用线级 tap（见第四节）抓 CLI 0.3.285 / 0.3.291 / 0.3.292 的真实请求，确认：

1. **环境加料融合在「当前轮」消息里发出**：CLI 把 `<system-reminder>` 环境块（工作目录、平台、日期等，数百字节）拼在当前轮用户消息的内容块最前面；**历史轮的消息不带它**（发纯文本）。因此相邻两轮的前缀断在"上一轮最后一条消息"处——每轮重写 ≈ 上轮加料 + 本轮新内容，历史部分照常命中。这是 CLI 的设计，**不是** 0% 的原因。
2. **计费头占据字节 0**：请求的 `system[0]` 是 CLI 塞的 `x-anthropic-billing-header: cc_version=<CLI 版本>.<三字符后缀>; cc_entrypoint=sdk-ts;`。后缀**按 CLI 安装指纹生成**（npm 重装后改变，进程重启不变），且 **fold 路径（首轮、降级、后台调用）与 resume 路径（正常轮）的后缀不同**。字节 0 一变，整个请求的缓存全部作废。
3. **断点位置**：CLI 只打两个 `cache_control`（1h TTL）——system 最后一项（覆盖它之前的全部系统提示词）和当前轮末尾。历史消息没有独立断点，它们靠"尾部断点覆盖的前缀"被缓存。
4. 三个 CLI 版本在受控环境下行为一致且健康：长对话模拟中逐轮稳定前缀占比随轮数增长，命中应有 90%+。

## 三、事故结论（2026-10-05 反馈）

用户症状：命中持续 0%，重 roll 有命中，回退 CCST 版本无效。根因三层：

1. **SDK 版本未锁**：`^0.3.285` 浮动 + lockfile 不入库，任意 `npm install` 把 CLI 拉到新版，新版改了加料方式 → 旧格式的逐轮回放全部错位。
2. **pin 不感知版本**：第一轮上下文做成 pin（`data/cli-context.json`）永久复用，跨版本继续回放错误字节 → 持续 0% 无法自愈。
3. **回退无效**：回退只回退代理代码，`node_modules` 里的 CLI 不降级；pin 文件跨版本留存。

**5.2.0 的修复**：SDK 锁死精确版本 + lockfile 入库 + Docker `npm ci`；pin 记录写入时的 SDK 版本、不符自动丢弃；连续 3 轮捕获失败 / 连续 2 轮「内容没变却没读到缓存」自动清空逐轮还原状态并在面板提示。

**如果用户升级后仍持续 0%**（重置无效即属此类）：问题在用户环境， tap 已证明三个 CLI 版本本身健康。按可能性排序：

- **双安装轮流应答**：同机「酒馆插件 + 独立代理」并存（#33 的双绑定场景），两份安装的计费头后缀不同，字节 0 每轮都变 → 持续 0%。处置：只留一份。
- 聊天中途 npm 重装过（后缀变化，一次性重写）。
- `node_modules` 里的 CLI 不是 0.3.285（5.2.0 只改 package.json，用户没重跑 `npm install` 的话还是旧版）。
- 每轮间隔超过 1 小时（缓存 TTL 到期，属正常现象）。

定位手段见下一节。

## 五、给用户的修复路径（按顺序）

1. 升级到 5.2.0+，在 CCST 文件夹跑一次 `npm install`（确保 SDK 真的换成锁定的 0.3.285），重启代理。升级后的第一轮会全量写一次缓存，之后恢复。
2. 还不行：删 `data/cli-context.json` 重启（手动触发 pin 重置）。
3. 还不行：跑 `node scripts/wire-diagnosis.mjs`，把输出发给维护者——输出会直接点名字节 0 是谁在变。
4. 判定是双安装：删掉不用的那份，只保留一个端口、一份安装。

## 六、附录：CLI 升级节奏与 clewdr 缓存机制（2026-10-07 取证）

### CLI/SDK 升级频率（官方数据）

- npm `@anthropic-ai/claude-agent-sdk`：9-15 → 10-06 的 22 天发了 **19 个版本**，基本每天一个；10-05 发 0.3.290（CLI 2.1.290）——正是"10-05 缓存 0%"反馈的当天。旧版浮动 `^0.3.285` 时，当天任何一次重装都会拉到新版，时间线完全吻合。
- CHANGELOG 2.1.290 里与请求字节直接相关的条目："修复代理/网关拒绝其中一个 beta 头（非 400 状态，或同时带第二个 beta）时请求失败"（beta 头发送方式变更，影响所有模型）与"修复续接的 subagent 丢失之前的 thinking 与 prompt cache"。
- 2.1.285（我们锁定的版本）则改了"自定义 ANTHROPIC_BASE_URL 会话使用 1M 上下文"。

### 旧线（CLI/SDK）维护协议

锁定版本后不会自动漂移；"调参"只发生在**主动升级**时。升级流程必须是：改 lockfile → 跑 `wire-diagnosis` 对比请求结构 → 跑命中率回归 → 发版。用户报"命中异常"时先问：最近是否重装过（拉到了新 CLI）。

### clewdr 的缓存机制（修正此前结论）

- `anthropic-wire` crate 有**全量 cache_control schema**（含 request 级"缓存整个请求前缀"的标记），但**放置逻辑为零**：订阅（code）通道是透传，断点由下游客户端负责；clewdr 只做检测、哈希，以及把下游断点里的 `scope` 字段剥掉。
- 官方文档（PR #88 `docs/cache_control_usage.md`）写明的机制：检测 system 里带 cache_control 的块 → 哈希 → **粘性 cookie 路由**（同 system prompt 固定同账号，Moka 缓存 1000 条 / 60 分钟 TTL）——这是 **cookie（网页版）通道**的账号级缓存保暖；订阅单账号通道用不上粘性路由。
- 计费头：clewdr 生成的 `claude_code_billing_header` 含**首条用户消息的哈希**（盐 `59cf53e54c78`）——按会话稳定、跨会话不同，与 tap 观测吻合。可作为新后端生成稳定计费头的参考公式。
- **对重写的意义**：clewdr 的实践佐证了"下游不打断点就没有缓存管理"——直连路线上断点必须由代理自己打（即 P2 cache 模块）。可借鉴：request 级 cache_control 标记（比逐块简单）、按会话稳定的计费头公式。
